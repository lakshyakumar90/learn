## How it works

<ScenarioPlayer scenario="node-phases" />

Node's loop executes callbacks while host facilities handle external waiting. Its phases and nextTick behavior are not the browser rendering cycle.

### Build the working version

<CodeRunner title="Build: The event loop in Node.js" expect="request received\nhealth check ready\nhandled 10000\nuse setImmediate for a Node check-phase yield\ncontract true">
{`const jobs = Array.from({ length: 10000 }, (_, id) => id);
async function handleBatch(queue, size) {
  let handled = 0;
  for (let start = 0; start < queue.length; start += size) {
    const batch = queue.slice(start, start + size);
    handled += batch.length;
    await sleep(0);
  }
  return handled;
}
console.log("request received");
const work = handleBatch(jobs, 1000);
const healthCheck = Promise.resolve("health check ready");
console.log(await healthCheck);
console.log("handled", await work);
console.log("use setImmediate for a Node check-phase yield");
const contractChecks = [jobs.length === 10000, (await work) === 10000];
if (!contractChecks.every(Boolean)) {
  throw new Error("The boundary contract was broken");
}
console.log("contract", contractChecks.every(Boolean));`}
</CodeRunner>

The console example proves callback order in a worker, not browser paint. The live frame runs on the page's browser thread; the worker button starts a separate worker. Node does not have a rendering phase.

## Why it works this way

The simulator omits some libuv phases. Main-module timeout versus immediate order is not portable; ESM startup also changes microtask context.

<ConceptCard variant="under-hood">
Keep the operation's contract separate from its implementation. A faster path is useful only when it preserves the same outputs, error behavior and ownership rules; validate those boundaries before relying on a host-specific optimization.
</ConceptCard>
