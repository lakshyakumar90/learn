## How it works

<Diagram id="js-runtime" />

Each call clears the previous timer and remembers the latest arguments. Quiet time permits the callback; cancel releases pending work.

### Build the working version

<CodeRunner title="Build: Performance patterns — debounce, throttle, memoization" expect="tea\nrequests 1">
{`function debounce(callback, delay) {
  let timer;
  function schedule(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => callback(...args), delay);
  }
  schedule.cancel = () => clearTimeout(timer);
  return schedule;
}
const queries = [];
const search = debounce((query) => queries.push(query), 5);
search("t");
search("te");
search("tea");
await sleep(15);
console.log(queries.join(","));
search("coffee");
search.cancel();
await sleep(15);
console.log("requests", queries.length);`}
</CodeRunner>

The console runner is an isolated browser worker. These core examples are also checked in Node; DOM behavior belongs to the browser frame, and fakeFetch is sample data rather than a real network request.

<CodeRunner title="Throttle continuous scroll work" expect="true\nfalse\ntrue\n10,30">
{`function throttle(callback, interval) {
  let last = -Infinity;
  return (value, now) => {
    if (now - last < interval) return false;
    last = now;
    callback(value);
    return true;
  };
}
const positions = [];
const onScroll = throttle((position) => positions.push(position), 100);
console.log(onScroll(10, 0));
console.log(onScroll(20, 50));
console.log(onScroll(30, 100));
console.log(positions.join(","));`}
</CodeRunner>

## Why it works this way

Debounce reduces requests but delays feedback. Throttle permits regular progress during a burst; neither prevents an older response overwriting a newer result.

<ConceptCard variant="under-hood">
Keep the operation's contract separate from its implementation. A faster path is useful only when it preserves the same outputs, error behavior and ownership rules; validate those boundaries before relying on a host-specific optimization.
</ConceptCard>
