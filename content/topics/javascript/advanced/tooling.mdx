### Build the working version

<CodeRunner title="Build: Tooling — npm, bundlers, transpilers, TypeScript" expect="valid\nquantity must be a positive integer\nname is required\nruntime checks protect external data\ncontract true">
{`function validateOrder(order) {
  const problems = [];
  if (typeof order.name !== "string") problems.push("name is required");
  if (!Number.isInteger(order.quantity) || order.quantity < 1) {
    problems.push("quantity must be a positive integer");
  }
  return problems;
}
const fixtures = [
  { name: "tea", quantity: 2 },
  { name: "rice", quantity: 0 },
  { quantity: 1 },
];
for (const order of fixtures) {
  const problems = validateOrder(order);
  console.log(problems.length ? problems.join("; ") : "valid");
}
console.log("runtime checks protect external data");
const contractChecks = [
  validateOrder(fixtures[0]).length === 0,
  validateOrder(fixtures[1]).length === 1,
];
if (!contractChecks.every(Boolean)) {
  throw new Error("The boundary contract was broken");
}
console.log("contract", contractChecks.every(Boolean));`}
</CodeRunner>

The console runner is an isolated browser worker. These core examples are also checked in Node; DOM behavior belongs to the browser frame, and fakeFetch is sample data rather than a real network request.

## Why it works this way

Keep development tooling outside the product flow. Browser integration tests cover host behavior that Node unit tests cannot.

<ConceptCard variant="under-hood">
Keep the operation's contract separate from its implementation. A faster path is useful only when it preserves the same outputs, error behavior and ownership rules; validate those boundaries before relying on a host-specific optimization.
</ConceptCard>
