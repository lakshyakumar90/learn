## How it works

<Diagram id="js-runtime" />

Calling a generator creates an iterator; next resumes its body to yield. Local position survives between requests.

### Build the working version

<CodeRunner title="Build: Iterators and generators" expect="first 1,2,3\nsecond 4,5,6\nlast 7\ndone true\nbatch size 2\nbatch size 2\nbatch size 2\nbatch size 1">
{`function* pages(records, size) {
  for (let start = 0; start < records.length; start += size) {
    yield records.slice(start, start + size);
  }
}
const records = Array.from({ length: 7 }, (_, index) => ({
  id: index + 1,
}));
const feed = pages(records, 3);
console.log(
  "first",
  feed
    .next()
    .value.map((row) => row.id)
    .join(","),
);
console.log(
  "second",
  feed
    .next()
    .value.map((row) => row.id)
    .join(","),
);
console.log(
  "last",
  feed
    .next()
    .value.map((row) => row.id)
    .join(","),
);
console.log("done", feed.next().done);
const freshFeed = pages(records, 2);
for (const batch of freshFeed) console.log("batch size", batch.length);`}
</CodeRunner>

The console runner is an isolated browser worker. These core examples are also checked in Node; DOM behavior belongs to the browser frame, and fakeFetch is sample data rather than a real network request.

## Why it works this way

Generators are not automatic caches or cancellation. Add cursors and use async iteration for network-backed pagination.

<ConceptCard variant="under-hood">
Keep the operation's contract separate from its implementation. A faster path is useful only when it preserves the same outputs, error behavior and ownership rules; validate those boundaries before relying on a host-specific optimization.

- Generators are not automatic caches or cancellation.
