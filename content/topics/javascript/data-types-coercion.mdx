JavaScript converts types behind your back in exactly the spots where money
and access checks live. Interviewers ask this to see whether you can predict
an expression's value — and defend user input against silent conversion.

## Real-life situation

A cart form sends price and quantity as strings. `"4" + 2` totals `"42"`
instead of `6`, and the order goes through overcharged. The fix is boring on
purpose: convert with `Number()` at the boundary, reject `NaN`, and compare
with `===` so types can never sneak past.

{`function cartTotal(price, quantity) {
  return price + quantity;
}
console.log(cartTotal("4", 2));

function safeTotal(price, quantity) {
  const cleanPrice = Number(price);
  const cleanQuantity = Number(quantity);
  if (Number.isNaN(cleanPrice)) {
    return "bad price";
  }
  if (Number.isNaN(cleanQuantity)) {
    return "bad quantity";
  }
  return cleanPrice + cleanQuantity;
}
console.log(safeTotal("4", 2));
console.log(safeTotal("four", 2));
console.log(safeTotal(4, 0));`}
</CodeRunner>

Try changing the last call to `safeTotal(4, "")` and explain why the result
is `4`, not `"bad quantity"`. Then try `safeTotal(0, 0)`. Log `typeof`
every value crossing a form boundary for a week; the habit pays for itself.

## When to convert, when to compare

Convert at boundaries (forms, URLs, storage) with `Number()` or `String()`
and nowhere else. Compare with `===` always; reach for `==` never. When `0`
or `""` are valid values, default with `??`, not `||`.

## Key takeaways

- `+` concatenates when either side is a string; convert inputs first.
- `===` compares type and value; `==` converts and surprises.
- Eight falsy values exist; empty arrays and objects are truthy.
