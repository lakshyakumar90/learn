`fetch` resolves on HTTP errors, browsers gate cross-origin reads, and
storage is strings-only — three facts that decide whether data code works.
Interviewers ask this because "await, await, ok" plus a CORS explanation
covers most real data bugs.

## Real-life situation

A profile loader awaits the user, then the avatar, then renders — but a 404
renders as a broken page instead of "user missing", because `fetch` never
rejected. Checking `res.ok` turns the silent bad render into a handled
empty state. Meanwhile a search box aborts its previous request on every
keystroke, so slow replies can't overwrite fresh ones.

## Cookies versus storages

Cookies travel with every request (sessions, auth flags) and hide behind
`HttpOnly`. `localStorage` persists per origin without traveling (themes,
drafts). `sessionStorage` dies with the tab (wizard state). Secrets go in
`HttpOnly` cookies, never in readable storage — one paragraph on XSS: build
markup only from trusted strings, or attacker text becomes your code.

## Key takeaways

- `fetch` needs two awaits plus an `ok` check; it rejects only on network failure.
- CORS failures are server configuration, not fetch bugs.
- Cookies travel, storages stay, sessions die with the tab.
