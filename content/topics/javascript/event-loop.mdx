One thread runs your code; everything slow waits in queues, and the loop
feeds them onto the stack when it's free. This page is the most-asked
JavaScript interview topic because the sync-timer-promise order puzzle
appears in screens, onsites and take-homes alike.

## Real-life situation

A dashboard logs "loading", fires a data fetch, schedules a refresh timer
and logs "ready". Users report the timer beating the data although both were
"immediate". The cause is queue priority, not speed: the promise reaction
drains as a microtask right after the script, while the zero-delay timer
waits a full loop turn. Knowing the order turns a mystery into a schedule.

Seen in: Node.js documents its loop phases, timers and `nextTick` ordering
in the official event loop guide (Node.js, 2009,
[event loop guide](https://nodejs.org/en/docs/guides/event-loop-timers-and-nexttick)).

## Browser versus Node, briefly

Browsers add a render step per turn; Node runs timer, I/O and check phases
per iteration. Both drain microtasks the same way. Node-only extras:
`process.nextTick` (before even promises) and `setImmediate` (next check
phase). Same mental model, different machinery.

## Key takeaways

- Sync runs first, microtasks drain completely, then one task per turn.
- Zero-delay timers still wait a full turn; promises don't.
- `await` parks the function, never the thread.
