<CodeRunner title="Build: Error handling" expect="loading finished\nready true 3\nloading finished\nfailed false\nHTTP 404\ncontract true">
{`async function loadDashboard(url) {
  try {
    const response = await fakeFetch(url, { latencyMs: 5 });
    if (!response.ok) throw new Error("HTTP " + response.status);
    const users = await response.json();
    return { ok: true, count: users.length };
  } catch (error) {
    return { ok: false, message: error.message };
  } finally {
    console.log("loading finished");
  }
}
const ready = await loadDashboard("/users");
console.log("ready", ready.ok, ready.count);
const failed = await loadDashboard("/missing");
console.log("failed", failed.ok);
console.log(failed.message);
const contractChecks = [ready.ok === true, failed.ok === false];
if (!contractChecks.every(Boolean)) {
  throw new Error("The boundary contract was broken");
}
console.log("contract", contractChecks.every(Boolean));`}
</CodeRunner>

The console runner is an isolated browser worker. These core examples are also checked in Node; DOM behavior belongs to the browser frame, and fakeFetch is sample data rather than a real network request.

## Why it works this way

Returning from finally can replace an earlier result or error. Catch where you can recover or add context rather than silently swallowing failure.

<ConceptCard variant="under-hood">
Keep the operation's contract separate from its implementation. A faster path is useful only when it preserves the same outputs, error behavior and ownership rules; validate those boundaries before relying on a host-specific optimization.
</ConceptCard>
