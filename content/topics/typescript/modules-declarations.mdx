Your typed code constantly meets untyped JavaScript: libraries, legacy
files, globals. Declaration files (`.d.ts`) describe those neighbors so
the checker can verify your side of the conversation. Interviewers ask
"where do the types for lodash come from?" — this page is that answer.

## Real-life situation

You install a small slug helper written in plain JavaScript. No
annotations, no checking — every call is a guess. A declaration file
bridges the gap: it promises `slugify(text: string): string` without
touching the library, and suddenly wrong calls fail in your editor. When
a library ships no types, the community DefinitelyTyped collection
(`@types/...` packages) usually has them.

Try changing the `code` annotation to `string` — clean. `typeof`
borrows a value's type without repeating it, which is exactly what a
`.d.ts` file contains: `declare function slugify(text: string):
string;` — a promise with no body. `import type` brings in only the type
meaning, so bundlers can drop the import entirely (Node's own type
stripping needs that keyword to erase imports correctly).

The static version of the bridge, build-checked below, shows the typed
side: the same promises a `.d.ts` file would hold, with bodies so the
page can verify them. The real `.d.ts` would contain only the `declare`
lines (shown as inline code above, never executed).

```ts
function slugify(text: string): string {
  return text.trim().toLowerCase().split(" ").join("-");
}
const shopVersion = "2.1.0";
const slug: string = slugify("Red Chair");
const tag: string = shopVersion;
console.log(slug + " " + tag);
```

## Key takeaways

- `.d.ts` files promise shapes for plain JavaScript — no rewrite needed.
- `typeof` borrows types; `import type` erases fully at emit.
- Missing library types? Look for `@types/...` first, declare second.
