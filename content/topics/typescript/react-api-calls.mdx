Components are functions with typed inputs; API calls are promises with
typed outputs. Interviewers ask you to type both live — props with an
interface, fetch with a generic envelope, and state that cannot hold the
wrong shape.

## Real-life situation

A login form takes a title and an `onLogin` callback, fetches the user,
and renders the name. Untyped, the callback receives whatever the form
feels like and the render trusts whatever the network sent. Typed, props
are checked at every usage, the response envelope is generic, and a
runtime guard stands where the network ends and your code begins.

Try fixing `bad` to `res.data` — clean. Props typing follows the same
shape-first habit, shown statically below with small declared helpers
standing in for React (no imports in the sandbox):

```ts
interface LoginProps {
  title: string;
  onLogin: (email: string) => void;
}
function useState<S>(initial: S): [S, (next: S) => void] {
  let current: S = initial;
  function set(next: S): void {
    current = next;
  }
  return [current, set];
}
function onSubmit(
  handler: (event: { preventDefault: () => void }) => void,
): void {
  handler({
    preventDefault: function (): void {},
  });
}
function LoginForm(props: LoginProps): string {
  const [email, setEmail] = useState("");
  setEmail("sam@example.com");
  onSubmit(function (event) {
    event.preventDefault();
    props.onLogin(email);
  });
  return props.title + ": " + email;
}
```

The event parameter needed no annotation — context provides it. State
keeps the type of its initial value. And the guard (`isUser`) is the
honest part: types describe your claims, but only a runtime check
confronts the network.

## Key takeaways

- Props are interfaces; events and state inherit types from context.
- Wrap fetch in a generic envelope, then guard the payload at runtime.
- A green check never proves the network behaved — validate at the edge.
