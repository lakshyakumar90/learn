Function signatures are contracts callers cannot wiggle out of: how many
arguments, in what order, of which types, and what comes back.
Interviewers test whether you read a signature the way the compiler
does — positionally, not by name.

## Real-life situation

A payment helper takes an amount and a currency. Someone calls it as
`chargeCard("USD", 25)` — names swapped. JavaScript charges twenty-five
"USD"s at runtime; TypeScript rejects the call before review. Add an
optional tip with a default, and the signature documents itself better
than any comment.

{`function chargeCard(amount: number, currency: string): string {
  const label = amount + " " + currency;
  return "charged " + label;
}
function withTip(amount: number, tip: number = 0): number {
  return amount + tip;
}
function runTwice(task: () => void): void {
  task();
  task();
}
console.log(chargeCard(25, "USD"));
console.log(withTip(20));
console.log(withTip(20, 5));
runTwice(function () {
  console.log("receipt printed");
});
console.log(chargeCard("USD", 25));`}
</CodeRunner>

Try fixing the last line to `chargeCard(25, "USD")` — the Types tab goes
clean. Then change `runTwice`'s parameter to `(code: number) => void` and
watch the anonymous function fail: callbacks are checked against the
parameter they are passed to, which is why inline handlers usually need
no annotations at all.

Optional parameters (`tip?: number`) may be skipped; default parameters
(`tip = 0`) fill themselves in. Overloads — several signatures, one
implementation — appear in library definitions; you will read them far
more often than you write them. For function values, see also
[closures](/topics/javascript/closures) in the JavaScript topic.

## Key takeaways

- Arguments match positionally: order and count are part of the contract.
- Defaults document themselves; callbacks inherit types from context.
- `void` means "ignore the result", not "returns nothing usable".
